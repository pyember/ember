# Ember v0.2 design

Status: accepted, implementation in progress on the `v0.2` branch.

Ember v0.2 is a rewrite. The v0.1 tree on `main` stays readable in git history for reference, but no
v0.1 module is carried over unless this document names it. The audit that motivated the rewrite found
126 distinct defects, 36 of them severe; most trace back to a few habits this design removes by
construction: globals used as dependencies, behaviour inferred by heuristics instead of declared,
several copies of one table or wire format, claims with no measurement, failures reported as success,
resources with no owner, and a library doing an application's work at import time.

## Goals

- Calling a model is one line, and every call reports exactly what happened: text, tool calls, a
  finish reason, token usage split by kind, cost when the price is known, and the provider request id.
- Independent model calls overlap automatically inside `@xcs.jit`, with no change to what the program
  computes. Section "xcs" states the guarantees.
- Compositions (ensembles, judges, votes, verifiers) are plain typed objects, and the NON notation
  compiles to them and runs.
- `import ember` performs no I/O, starts no threads, and cannot fail because of a config file.
- Every public example in the README runs in CI against a fake provider.

## Non-goals for v0.2

- Automatic differentiation or JAX integration. JAX users call JAX directly.
- Bedrock and Vertex adapters. OpenAI-compatible endpoints (Azure v1, Ollama, vLLM, any gateway) are
  covered by one adapter.
- Request deduplication or provider batch APIs. Deduplication would break sampling at temperature > 0.
- Live model discovery. The catalog is data in the repository; unknown models still work (below).
- Gemini's Interactions API. Google now recommends it as the default and calls `generateContent`
  legacy but supported; v0.2 ships a `generateContent` codec because it is stateless per request
  like every other codec here. An Interactions codec is the first follow-up for Gemini.

## Layout

Folders follow features, and dependencies point one way:

```
ember/errors.py      one error type for model calls, a few for config and usage
ember/context.py     immutable configuration, one contextvar, override layers
ember/config.py      the config file: one reader, one atomic writer, redaction
ember/xcs/           the concurrency runtime: scheduler, jit, map, recorded graphs
ember/llm/           model calls: catalog, request/result types, client, providers
ember/operators/     Operator, Chain, Ensemble, Judge, Vote, Verify, @op
ember/non/           the NON grammar and its compiler to operators
ember/data/          dataset streaming (optional extra)
ember/eval/          evaluation runs that record every request's outcome
ember/cli/           `ember` command
```

Allowed imports: `errors` <- `context`, `config` <- `xcs` <- `llm` <- `operators` <- `non`; `data` and
`eval` may use `llm`, `operators` and `xcs`, and `eval` may also use `data`; `cli` may use anything.
Nothing imports `cli`. A test enforces this table.

## Dependencies

Core: `httpx`, `pydantic`, `pyyaml`, `greenlet`. Ember speaks each provider's HTTP API directly through
its own codecs, so no provider SDK is required. Extras: `data` (`datasets`, `huggingface-hub`), `dev`.
No exact pins and no upper caps without a written reason next to the pin.

## Errors

`ember.errors` defines:

- `EmberError(Exception)`: base of everything ember raises on purpose.
- `ConfigError(EmberError)`: unreadable or invalid configuration, missing credentials.
- `ModelError(EmberError)`: any failed model call. Fields: `kind: ErrorKind`, `provider: str`,
  `model: str`, `status: int | None`, `request_id: str | None`, `retry_after_s: float | None`. The
  message is built from these fields and a short reason string; it never embeds upstream response
  bodies, file paths or credentials.
- `ErrorKind` (closed enum): `AUTH`, `PERMISSION`, `QUOTA` (credit, spend or usage quota
  exhausted), `NOT_FOUND`, `BAD_REQUEST`, `RATE_LIMITED`, `OVERLOADED`, `SERVER`, `MALFORMED` (the
  provider answered but the response could not be decoded; retrying would repeat a billed call),
  `TRANSPORT`, `UNPRICED`, `CANCELLED`. `ModelError.retryable` is derived from the
  kind: `RATE_LIMITED`, `OVERLOADED`, `SERVER`, and `TRANSPORT` before the first response byte.
- `NonSyntaxError(EmberError, ValueError)`: invalid NON specification, with the column of the error.

Truncation, refusals and content filtering are not errors: they are finish reasons on the result.

## Context and configuration

- One `contextvars.ContextVar[Context]`. No thread-locals, no module globals holding state.
- `Context` is immutable. `ember.context.current()` returns the active one; the first call builds the
  root from the config file, which is the first moment ember reads disk.
- `with ember.context.override(...)` pushes an immutable layer and restores the previous context with
  the token it received, so nested and concurrent use is safe. Overrides are never written to disk.
- Credentials resolve in this order: an override, the provider's standard environment variable
  (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, or the one named in that provider's config),
  then the config file. A missing credential raises `ConfigError` naming the variable to set. Ember never
  prompts, never launches a setup program, and never writes a key it was not explicitly asked to save.
- Every task ember runs on another thread or greenlet runs inside a copy of the caller's context.
- `ember.config` owns `~/.ember/config.yaml` (or `EMBER_CONFIG`): one reader, one atomic writer with
  mode 0600, and one redacting serializer used by every CLI path that prints configuration. Every
  error names the file and, when the problem is at a key, its line, and never chains the YAML parser's
  error (which quotes the offending line). Retry values must be finite numbers. `save_provider_field`
  and `remove_provider_field` (which accepts any field name, so a misspelt key can be removed)
  validate the result before writing it.
- Provider names are lowercase letters, digits and `_`, starting with a letter, at most 32
  characters; `base_url` is an http or https URL; `api_key_env` is an environment variable name.
  These values are shown unmasked, so each has a format a misplaced key cannot pass, and the errors
  describe the format without repeating the value.
- The writer keeps the file's key order, fsyncs the new file and (except on Windows, which cannot
  open a directory to sync it) its directory before and after the atomic rename, and refuses to rewrite a file that has comments (they would be lost), naming the
  first comment's line. It takes no lock: two processes writing at the same moment can lose one
  update, because the standard library has no portable file lock. Writes come only from
  `ember configure`, so this needs two concurrent commands.
- `redacted` masks keys to their last four characters and removes the user information (with or
  without a scheme) and query string of URL fields, where credentials are sometimes embedded.
- `provider_fields(path)` lists each provider entry and the fields it sets without validating values,
  so the CLI can check what a repair would remove from a file `load` rejects.
- `ConfigData.path` is the file the data came from. `ember.context.from_config(data)` builds a
  `Context` from validated file data and prefixes any error with that path; the root context and the
  CLI both build contexts this way.

## Models (`ember.llm`)

### Names and the catalog

- A model is named `provider/name`, for example `openai/gpt-5` or `anthropic/claude-sonnet-4-5`. The
  string is parsed once into `ModelRef(provider, name)` at the API boundary and never re-split.
- The catalog is one data file, `ember/llm/catalog.toml`, loaded once into an immutable `Catalog`. Each
  entry (`ModelSpec`) holds the provider, the wire id sent to the API, aliases, context window, maximum
  output, which wire API it uses, the allowed reasoning efforts, which sampling parameters it accepts,
  and its rates. Every rate carries the URL of the provider's published price page and the date it was
  read.
- Resolution: an exact catalog id or alias resolves to its spec. A `provider/name` that is not in the
  catalog still works when the provider is known: the name is sent as the wire id and the spec is
  marked unknown, so the context window and price are unknown. A bare name that is not an alias raises
  `ModelError(NOT_FOUND)` before any request is sent. No prefix guessing and no network discovery.

### Requests

`Request` is a frozen dataclass: `messages: tuple[Message, ...]`, `system: str | None`,
`tools: tuple[ToolSpec, ...]`, `tool_choice`, `sampling: Sampling`, `output_schema`, and
`extensions: Mapping[str, object]` for provider-specific fields that the caller names explicitly.
Extensions merge into the wire body recursively, so `{"reasoning": {"summary": "auto"}}` adds to the
`reasoning` object ember built; a field ember already sets, at any depth, is a `ValueError`, never an
override. `Message` has a role and a tuple of typed parts (`TextPart`, `ImagePart`, `ToolCallPart`,
`ReasoningPart`, `ToolResultPart`). Invalid combinations raise when the request is constructed, before
anything is sent. The public call accepts these fields as explicit keyword arguments; there is no
`**kwargs` bag.

`ReasoningPart(text, api, provider, state)`, allowed only in assistant turns, holds reasoning a provider
must see again when a conversation continues: Anthropic `thinking` and `redacted_thinking` blocks
(signature included; a modified block is rejected), OpenAI Responses `reasoning` items (with
`encrypted_content` when present), and Gemini thought signatures. `text` is the readable reasoning,
empty when the provider sent only encrypted or redacted state; `state` is the provider's own item. A
codec replays `state` verbatim only when both `api` and `provider` match the model the request goes
to, so one provider's state never reaches another (an OpenAI-compatible gateway never receives OpenAI
state); every other request leaves the part out. A different model at the same provider receives the
state and the provider decides; if it rejects it, the call fails with `BAD_REQUEST`. A Gemini
signature rides on a specific part: its `ReasoningPart` comes directly before the text or tool-call
part it arrived on, and encoding puts it back on that part.

### Results

`Result` is a frozen dataclass: `text`, `tool_calls`, `finish_reason: FinishReason` (closed enum:
`STOP`, `LENGTH`, `TOOL_CALLS`, `CONTENT_FILTER`, `REFUSAL`), `usage: Usage`, `cost: Money | None`,
`model: ModelRef`, `request_id: str | None`, `latency_s: float`, and `message: Message`, the assistant
turn (text, reasoning and tool calls in provider order) that a caller appends to the history unchanged,
followed by its tool results, to continue the conversation. The client copies it from the provider's
`Decoded.message`; a response with no content is the turn `(TextPart(""),)`.

`Usage` splits tokens into `input` (uncached), `cache_read`, `cache_write`, `output` (including
reasoning) and `reasoning` (the part of `output` spent reasoning), plus `measured: bool`. Ember never
estimates token counts; a provider that reports none yields `measured=False` and zeros.

`Money` is an integer number of nano-dollars, so three tokens at $0.15 per million cost 450, not
zero. Cost is computed once per call from the spec's rates, exactly, with one final rounding. When the provider reports its own cost, that figure wins. When the
model has no known rate, `cost` is `None`; a context option `require_price=True` turns that into a
`ModelError(UNPRICED)` raised before the request is sent.

### Calls and pending results

The public call, exported as `ember.models`:

```python
models(
    model: str | ModelRef | None,          # None uses the context's default_model
    prompt: str | Sequence[Message],
    *,
    system: str | None = None,
    tools: Sequence[ToolSpec] = (),
    tool_choice: ToolChoice = "auto",
    temperature: float | None = None,
    top_p: float | None = None,
    max_output_tokens: int | None = None,
    stop: Sequence[str] = (),
    seed: int | None = None,
    reasoning_effort: str | None = None,
    output_schema: Mapping[str, JsonValue] | None = None,
    extensions: Mapping[str, JsonValue] | None = None,
) -> Completion

models.stream(...same arguments...) -> Iterator[Event]
models.bind(model, **same keyword defaults) -> BoundModel   # a callable taking the prompt
```

A model string is either `provider/name` or a catalog alias such as `gpt-5`. Settings a model does
not accept (for example `temperature` on a model that rejects it) raise `ValueError` before sending.
`ember.llm.Client` exposes the same calls for callers who construct their own client and
provider factory instead of using the context's default.


`ember.models(model, prompt, ...)` returns a `Completion`. A `Completion` is a `Result` that may still
be in flight: the request has already been built from the call-site arguments and sent, and reading any
field waits for it. Outside `@xcs.jit` the call waits before returning, so it behaves like a plain
synchronous call. Inside `@xcs.jit` it returns at once (section "xcs").

`ember.models.stream(...)` yields typed events: `TextDelta`, `ReasoningDelta`, `ToolCallDelta`,
`UsageEvent`, and a final `Done(result)`. Text and tool calls never share a channel.

### Providers

A provider is a codec plus a transport, and every call streams: `send` reads the stream to its end and
returns the final `Decoded`. A non-streamed response sends no byte until generation ends, so streaming
is what makes the idle bound a liveness bound rather than a cap on generation time. The codec is pure:
`encode(spec, request) -> body` builds the streaming request, `decode_events(spec, sse_events,
request_id)` yields deltas and ends in exactly one `Decoded` (`spec` names the provider that reasoning
parts belong to), and `classify(status, body)` maps an HTTP error to a kind from the provider's own
error code first and its status second. Quota, billing and spend-limit codes (OpenAI
`insufficient_quota`, `credit_balance_exhausted`, `*_spend_limit_exceeded`, `*_usage_limit_exceeded`;
Anthropic `billing_error`; HTTP 402) are `QUOTA`, and a response ember cannot decode, including one
that raises an unexpected exception inside a codec, is `MALFORMED`. A failure sets
`ModelError.before_first_byte` by whether any item reached the caller, so a `send` failure is always
before the first byte. Codecs are tested against fixtures taken from each provider's API reference.
The transport owns one long-lived `httpx.Client` per provider configuration, adds authentication, and
maps HTTP failures to `ModelError` kinds. Adapters never retry.
`ember.llm.providers.build(settings, ctx, *, transport=None)` constructs a provider; `transport`
replaces the network in tests.

Reasoning effort is sent as each API documents it: `reasoning_effort` (Chat), `reasoning.effort`
(Responses), `output_config.effort` (Anthropic, API version 2026-10-21, which also removed
`temperature` and `top_p`; manual thinking budgets are rejected by current Claude models, so there is
no effort-to-budget table), and `thinkingConfig.thinkingLevel` (Gemini 3 and later).

Shipped codecs: OpenAI Chat Completions, OpenAI Responses, Anthropic Messages, Gemini
`streamGenerateContent`. Responses requests to a reasoning model ask for
`reasoning.encrypted_content`, so replaying reasoning never depends on the provider storing the
response. A Gemini function call that arrives without an id gets an ember id unique to its response
and position, and is sent back, with its response, without an id, because Gemini pairs id-less calls
by name and order. Gemini image URLs must be Files API URIs. Shipped providers: `openai`, `anthropic`, `gemini`, and `openai_compatible`, which is
OpenAI Chat Completions at a configured base URL under a provider name the user picks. Azure OpenAI
uses it with the `https://<resource>.openai.azure.com/openai/v1` base URL, which takes the key as a
bearer token and needs no `api-version`.

Timeouts are connect and idle bounds (no byte for N seconds), never a cap on total generation time.

### The client

`Client` resolves a `ModelRef` against the catalog, checks price policy, acquires capacity from the
provider's limiter, sends, and builds the `Result`. It is the only place that retries: it retries
`ModelError`s whose kind is retryable, at most a configured number of times, with jittered backoff
that honours `retry_after_s`, and never after the first response byte of a stream. The limiter is
additive-increase/multiplicative-decrease, grows only while saturated, and hands out single-use
permits.

### How model calls meet the scheduler

`ember.llm` reaches the scheduler only through `ember.xcs.runtime`:

- The client acquires a rate-limit permit before sending. `Limiter.acquire(provider)` returns a
  future that completes when capacity is free, and the client reads it with `runtime.wait`, so a
  call waiting for capacity lets other greenlets run.
- The client then hands the request to `runtime.dispatch` (or `runtime.dispatch_stream` for
  streaming). Worker threads therefore only run requests that already hold a permit, and they never
  wait on other ember work. A provider at its limit cannot block requests to other providers.
- Every result, including a permit, is read through `runtime.wait`.
- The limiter keeps acquirers waiting for capacity in a `runtime.WaitQueue` (`push`, `pop`, `len`)
  under its own lock, and gives each freed slot to `pop()`. The scheduler decides the order: arrival
  order across jit calls, so no call starves another, and within one jit call the request with the
  longest predicted remaining path first. `push` runs on the acquiring greenlet, which is how the
  queue knows which call and which request is waiting; `pop` may run on any thread.
- `runtime.deferred()` says whether the caller is inside `@xcs.jit` or `xcs.map`. Outside, a model
  call waits for its result before returning and raises its error at the call site. Inside, it
  returns a pending `Completion` and the error raises on first read, or at the jit boundary if
  never read. The rule depends only on scope, never on whether a request happened to finish
  before `dispatch` returned. Errors found before sending (an unknown model, a setting the model
  does not accept, an unpriced model under `require_price`) raise at the call site in both cases.
- Retries run inside the dispatched task, which holds its permit through backoff. The worker
  pool must therefore never be a tighter bound than the permits: a provider backing off must not
  delay requests to another provider. The pool starts a thread whenever none is idle, and idle
  threads exit. Handing a task to the pool is all or nothing: if no thread can start, `dispatch`
  raises at the call site and the request is never sent or waited for.
- `dispatch_stream` sends the request at its call site, inside `@xcs.jit` and outside it: a worker
  drains the stream into a buffer bounded by the response, not by a fixed size (a full fixed-size
  buffer would make the worker wait on its reader, which may itself be waiting for a queued
  request). Outside a scope it returns once the stream has produced its first item or ended.
- A stream's failure is raised only to a reader that pulls it. A failure the reader never pulls is
  never raised, whether the reader was closed, dropped or kept alive unread, as with any Python
  iterator. Closing or dropping the reader abandons the stream: the worker stops when its next item
  arrives (generation and billing stop), and the client reports the attempt as `CANCELLED`.
  Dropping only releases sooner what the boundary would release anyway; no outcome depends on when
  a reader is collected. At a jit boundary every stream not read to the end is abandoned, and the
  boundary waits only for that to take effect; reading such a stream afterwards raises
  `RuntimeError`.

### Observing attempts

`ember.llm.observe.observing(observer)` installs an observer for a block. The client reports every
attempt of every call made in that block, retries included, as an `Attempt` (call id, attempt number,
model, latency, the `Result` or `ModelError`, and whether it will retry). `ember.eval` builds its
per-request records on this; nothing else needs a callback.

`on_attempt` runs inside the dispatched task, so under `@xcs.jit` and `xcs.map` it runs on worker
threads, possibly several at once and alongside user code. Observers must be thread-safe. This is the
one exception to "user code never runs in parallel with other user code" (section "xcs").

## xcs

### `@xcs.jit`

Decorating a function with `@xcs.jit` changes when model calls wait, never what the function computes.

Inside a jit call, every model call builds its request from the arguments as they are at the call
site, sends it immediately, and returns a pending `Completion`. The function keeps running. Reading a
field of a pending `Completion` waits for that call only. Python runs the function exactly once, in
program order; only network waits overlap. Independent calls written one after another therefore run
concurrently, and a step that reads earlier results waits for exactly those results.

Guarantees, each covered by a test:

- Each model request and each user function body runs exactly once per call.
- A request is built from the values its arguments had at the call site.
- No value is read before it is complete, and nothing is cached across calls.
- Within one jit call, user code never runs in parallel with other user code. Functions started by
  `xcs.map` interleave only at points where one of them reads a pending result. The one exception is
  an attempt observer's `on_attempt`, which runs on worker threads (section "Observing attempts").
- An error is raised with its original type when the failed value is first read, or when the jit call
  returns if it was never read. Every pending call created inside a jit call has finished before it
  returns.
- The context active at a call site is the context its request uses.
- At most a configured number of requests are in flight per provider; beyond that, the call that
  would exceed it waits.

Failures beyond the one raised are attached to it as notes. A scope ends with its outermost call:
code that runs later in a context captured inside it (an asyncio callback scheduled in the body, say)
is outside it, so `deferred()` is False there. A process forked inside a scope cannot wait in it: the
child's first wait raises `RuntimeError`. The body runs on the caller's own
greenlet and context, so context changes it makes persist as they would in a plain call. `jit`
rejects async functions and generator functions with `TypeError`, because their bodies would run
after the boundary.

### The graph

Each jit call records the graph it executed: nodes are model calls (streams included), and an edge
means a request was built after its greenlet read the other node's result, directly or through
results that depended on it. `jit(f).graph()` shows the nodes, edges, measured timings and the
critical path (the chain of dependent calls with the largest total duration) of the last run.

The outermost jit call also keeps its graph as a plan, keyed by each call's place in the program:
the spawn path of the greenlet that made it and how many calls that greenlet had made before, which
timing does not change. When requests wait for capacity in a `runtime.WaitQueue`, freed slots go to
jit calls in arrival order, so no call starves another, and within one jit call to the request with
the longest predicted remaining path. A run that departs from the plan drops it for that run. The
graph is never replayed in place of running the function, and no request is sent before the program
reaches it.

Operators and NON graphs declare their structure, so `jit` compiles them ahead of execution and can
plan the whole graph before the first request: critical-path order under rate limits, and token and
cost bounds from the catalog, labelled as bounds.

### `xcs.map`

`xcs.map(fn, items)` runs `fn` on each item concurrently and returns the results in order. Each item
runs in its own greenlet on the caller's thread with a copy of the caller's context; only network I/O
uses worker threads, and worker threads never wait on other work, so nesting cannot deadlock. Items
start in order, each running until it first waits before the next starts, so every item starts before
any continues past a wait. If an item raises, no further items start, in-flight items finish, and the
first error by item order is raised. A `map` outside any jit call is a boundary of its own, like one.

An interrupt (a `BaseException` that is not an `Exception`, such as `KeyboardInterrupt`) is different:
raised in an item, or arriving while the map waits, it stops the map at once. Every started item that
has not finished is held (neither it nor anything it started resumes), then each gets `GreenletExit`
where it waits, so its `finally` blocks run and it sends nothing more, and the interrupt is raised
once they have unwound. An item whose `finally` block waits does not let the others run meanwhile. Requests already sent still finish before
the enclosing jit call returns. An interrupt that arrives while the thread waits for results is
raised in the jit body; if the body catches it, the scope keeps working.

The scheduler uses `greenlet`, which is a core dependency.

## Operators

An operator is a frozen, slotted dataclass that implements `forward(self, input: In) -> Out`, typed as
`Operator[In, Out]`. `dataclasses.replace` is the only way to change one. Validation is optional and
declared in one place: `input_model` and `output_model` class attributes holding pydantic models with
`extra="forbid"`, checked at the call boundary. Nothing is inferred from parameter names or annotations.

Built-ins: `ModelCall` (prompt template plus model), `Chain`, `Ensemble`, `Judge`, `MajorityVote`,
`Verifier`. `Ensemble(members, quorum=..., deadline_s=...)` runs members through `xcs.map` and returns
each member's outcome. An empty ensemble cannot be constructed. `@op` turns a function into a
`FunctionOperator` at decoration time.

## NON

One grammar, parsed by a tokenizer, no legacy form:

```
graph  := stage ("," stage)*
stage  := count TYPE "@" model params?      for E, J, V
        | count "M"                          majority vote, no model
model  := provider "/" name                  name may contain ":" "." "-" "_"
params := "(" key "=" value ("," key "=" value)* ")"
```

`TYPE` is `E` (ensemble), `J` (judge), `M` (majority vote) or `V` (verifier); counts are at least 1;
parameter values are typed by the stage's schema and duplicate keys are errors. `build_graph(spec)`
returns an `Operator` that runs.

## Data and eval

### `ember.data`

- `Example(question, answer, choices=(), metadata={})` is the one record type. Every field is
  type-checked when the example is built (`ValueError`, so a stream can name the row); `choices` is a
  tuple of strings and `metadata` is copied and left out of the hash. For a multiple-choice question
  `answer` is the letter of the correct choice (`"A"` for the first), checked against the number of
  choices.
- `Dataset(path, config, split, to_example, revision=None)` names a Hugging Face Hub dataset and maps
  each raw row to an `Example` with a function written for that dataset. Nothing is inferred from
  field names; a row that does not fit raises `ValueError` naming its position.
- `DATASETS` is one immutable table of named datasets, each pinned to a Hub commit: `mmlu`
  (`cais/mmlu`, `all`, `test`, commit `c30699e8`; the answer index becomes a letter) and `gsm8k`
  (`openai/gsm8k`, `main`, `test`, commit `740312ad`; the answer is the number after `####`, the
  worked solution goes to `metadata["solution"]`). Moving a pin is a reviewed change. There is no
  registration API and no entry points; a caller with another dataset passes their own `Dataset`.
- `stream(name_or_dataset, split=None, limit=None)` opens the dataset when called (a missing extra,
  unknown name, empty or unknown split fails there, and an unknown name never reaches the network) and
  returns a `Stream` of examples that also carries its `Source` (path, config, split, revision,
  limit). `datasets` is imported only inside `stream`; an `ImportError` is reported as the missing
  extra only when the missing module is `datasets` or `huggingface_hub`. `trust_remote_code` is never
  set.

### `ember.eval`

- `run(task, items, scorer=..., records=path, item_errors=(ModelError,))` applies `task` to each item
  in order, scores each output, and returns `RunRecords`. Each item runs inside
  `ember.llm.observe.observing(...)`, so every request attempt it causes is attributed to it. The
  item is encoded before the task runs, so an item that cannot be recorded is never sent. The task,
  the scorer and the output encoder all run inside the item's error handling, because under
  `runtime.deferred()` a call's error raises when its result is first read. An exception in
  `item_errors` fails only its item, which is recorded with the error and no score; any other
  exception stops the run after an end record naming it is written, and is re-raised.
- Encoded items and outputs are normalized once to plain JSON types (lists, dicts, scalars), and that
  value is both written and returned, so `run(...)` equals `read_run(path)`.
- Records are JSON lines, written and flushed as each item finishes, to a file that must not exist.
  Every line has `"schema": 1` and a `type`: `run` (header: run id, start time, ember version, scorer,
  and the `Source` when the items were a `Stream`),
  `item` (index, item, latency, outcome `scored` with output, score and extracted answer, or `failed`
  with the error; and every attempt: call id, attempt number, model, latency, request id, whether it
  was retried, and either finish reason, usage and cost in nano-dollars, or the error kind, status and
  message), and `end` (elapsed time, the abort if any, and the summary). Item records appear in
  the order items finished (so a run that dies loses no finished item); each index appears once,
  a finished run has every index from 0, and `RunRecords.items` is in index order. A file without an `end` line was cut off mid-run and still reads, with `end` a
  `CutOff`; an unterminated last line that does not parse is the record being written when the
  process died, and is dropped and reported. `read_run(path)` returns the same `RunRecords` and
  rejects a bad line anywhere else, an unknown outcome, items out of order, or a written summary that
  does not match the items.
- `Summary` is computed from item records only: items, scored, failed (by error kind), mean score over
  scored items, calls, attempts, retries, failed attempts and calls, unpriced and unmeasured calls,
  cost of priced calls and tokens of measured calls. Nothing is dropped to make a number look better.
- Scorers state one extraction rule each: `ExactMatch` (surrounding whitespace ignored), `NumericAnswer`
  (the last number, or the first after a given marker; values compared exactly), and `MultipleChoice`
  (the last `Answer:` line whose rest is a choice's letter followed by nothing or by exactly that
  choice's text, so "Answer: C) 4" chooses C when C is "4" but "Answer: A careful reading..." is not
  an answer; `multiple_choice_prompt` asks for that format). None gives credit for
  an answer that only appears somewhere in the output.
- Evaluation never executes model-written code. v0.1's code-execution evaluator ran it in a subprocess
  with a regex blocklist and resource limits, which is not a sandbox; a sandboxed runner is future
  work with its own design.

## CLI

`ember` parses its arguments before reading any file, so a broken config cannot stop it. Errors ember
raises on purpose print as one line and exit 1; usage errors exit 2.

- `ember configure show` prints the config file through `config.redacted` and then checks it loads.
- `ember configure set-key PROVIDER` reads the key with `getpass`; keys are never accepted in argv.
- `ember configure set PROVIDER {kind,base_url,api_key_env} VALUE` and
  `ember configure unset PROVIDER [FIELD]` change one field. A change to a config that loads is
  written only if the config still loads afterwards; a change to a config that already fails to load
  is written anyway, since it may be the repair, and the command reports what still fails. `unset`
  accepts misspelt field names. A config file with comments is never rewritten (see `ember.config`).
- Output is built from an allowlist: it never repeats a name or value typed on the command line
  unless it is already known (a provider in the file or built in, a field name, a kind, a
  subcommand), because a key typed in the wrong place must never be printed. The parser's errors are
  built from its own definition, never from argparse's message; an unknown provider, field or kind is
  named by its role (`PROVIDER is not a configured provider; known: ...`). A test puts a key in every
  positional and option slot of every subcommand and checks it never appears in any output.
- Pending, waiting on the catalog: `ember models` lists the catalog; `ember check MODEL` sends one
  short request and reports the result's finish reason, latency, request id, usage and cost, or the
  error.

No setup wizard, no interactive prompt besides `getpass`, no subprocesses.

## Testing

- Unit tests run with no network: providers are exercised through recorded wire fixtures and a fake
  transport.
- The xcs oracle: for every program in `tests/oracle/`, `jit(f)(x) == f(x)`, the multiset of provider
  requests is identical, the side-effect log is identical (program order) for jit and per-item order
  for `map`, and wall time with independent calls is at most the plain run's. Oracle programs live in a
  module whose name matches nothing ember treats specially.
- Every README code block runs as a doctest against the fake provider.
- An import test asserts that `import ember` succeeds with an unreadable config file, starts no
  threads, and imports no provider or data dependency.

## CI

One workflow on `runs-on: ${{ vars.CI_RUNNER || 'ubuntu-latest' }}`: `ruff check`, `ruff format
--check`, `mypy --strict src`, tests on Python 3.11 and 3.13, `uv lock --check`, and a job that builds
the wheel, installs it into a clean environment and imports ember.
